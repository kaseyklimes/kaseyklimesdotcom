# Private website analytics

The owner dashboard is at `/insights`. It covers traffic over 7, 14, 30, 90, 180, 365, or 730 UTC calendar days, year-to-date, custom dates, and all time, page attention, card exposure and conversion, acquisition, campaign tags, device/country segments, content topics/formats/editorial emphasis, and page-to-page journeys. No historical data is backfilled.

## Security and configuration

The report API validates an HMAC-signed owner cookie on every request. The dashboard is dynamically rendered and never cached. Public pages retain static rendering. Login uses a scrypt password hash, distributed rate limiting (5 attempts per 15 minutes per IP), strict origin checks, and an 8-hour HttpOnly, Secure, SameSite=Strict cookie. No registration or other users exist. The access key is a generated 192-bit secret; possession grants owner access.

Run `node scripts/analytics-credentials.mjs` once to generate `.env.analytics.local` with mode 0600. The script refuses to overwrite a file. The owner access key is in the first comment; save it to a password manager. Only the password hash and signing secret belong in deployment environment variables. Never commit this file or expose credentials using `NEXT_PUBLIC_` variables.

Required production environment variables:

- `KV_REST_API_URL` and `KV_REST_API_TOKEN`, supplied by the Vercel Upstash integration. Alternatively use `ANALYTICS_REDIS_URL` and `ANALYTICS_REDIS_TOKEN`.
- `ANALYTICS_PASSWORD_HASH` — `salt:scryptHash`, generated by the script.
- `ANALYTICS_SESSION_SECRET` — generated random signing secret, at least 32 characters.
- `ANALYTICS_SITE_ORIGIN` — exact canonical origin, currently `https://kaseyklimes.com`. Its exact `www` counterpart is also allowed because both currently serve the website.

Store authentication variables as sensitive in Vercel Production. Do not connect Preview deployments to production analytics storage. Missing configuration fails closed. For owner-key rotation, generate a new credential file, replace **both** the password hash and session secret, and redeploy. Changing the signing secret revokes existing sessions. Sign out deletes the current browser's cookie.

The collector accepts only same-origin POST batches of at most 30 events/16 KB. Bodies are bounded while streaming. Input schemas, event names, URL paths, IDs and numeric fields are validated. Collection is limited to 120 requests per minute per IP, using an HMAC of the Vercel-provided client IP. Raw IPs are not saved in event records. This trust model assumes direct deployment on Vercel; non-Vercel instances use a shared local rate-limit identity.

## Measurement definitions

- **Session:** random tab-scoped sessionStorage ID. A new session begins after 30 minutes without a new page view. Sessions are not unique people and cannot link a visitor across devices, tabs, or long absences.
- **View:** a client-side route visit. SPA navigation is tracked; prefetches are not. Browser privacy signals, opt-outs, owner sessions, and common bots are excluded. Ad blockers and network loss reduce coverage.
- **Engaged view:** at least 10 measured active seconds. Time accrues only while the tab is visible and activity occurred in the previous 60 seconds; capped at 30 minutes/view. Heartbeats carry cumulative totals, and aggregation uses the maximum, not their sum.
- **Scroll:** greatest fraction of document height visible; short pages may reach 100% immediately. It is not proof that content was read.
- **Card impression:** schema 2 requires half of the card’s viewport-capped area visible for one continuous second in a visible tab, so oversized cards remain measurable. The existing CTR deduplicates by card/page view; the new funnel distinguishes each presentation within that view. Older unversioned impressions used half the full card area and cannot be compared as identical measurement.
- **Card CTR:** page views with a card click _and_ its recorded impression divided by page views with an impression. External card clicks count separately from outbound destination clicks. Impression denominators exclude unmeasured exposure.
- **Source:** session entry's `utm_source`, otherwise referring domain, otherwise Direct / unknown. Medium and campaign come from `utm_medium` and `utm_campaign`. These are caller-supplied analytics labels, not verified identities.
- **Country/device:** coarse Vercel geolocation and user-agent device class, both approximate. No sensitive demographics or employer identities are inferred.
- **Content dimensions:** current Markdown metadata, not a historical snapshot. Multi-tag pages contribute to each tag. Editorial emphasis is the existing 1–5 stars value used for grid placement, not a visitor rating.
- **Journeys:** actual consecutive distinct paths. A content filter only retains transitions whose endpoints both match; it does not fabricate a connection across excluded pages. Last observed pages are not confirmed exits.

The source/content matrix shows engagement rates with engaged/total view denominators. All comparisons are observational; audience size, placement, campaign mix, and small samples can explain differences.

## Storage and operations

Redis atomically compacts incoming events into one durable summary per page view: source/device/country, session identifier, maximum active time and depth, and sets of exposed/clicked cards, destinations and media actions. Repeated heartbeats and retry batches cannot inflate results. These summaries **do not expire**: all-time means all successfully captured history since tracking began. No history is fabricated for the years before deployment. Outbound and interaction metrics count views with an action, not every repeated click within a view.

Collection has a 20,000-input-event daily limit and a 128 MiB serialized-storage budget with an overhead allowance. Reaching a cap records a coverage warning and stops additional storage growth; existing history is never silently pruned. The free provider's separate command/bandwidth limits can also affect availability. Upgrade capacity deliberately when needed. Rate-limit keys expire in 1 or 15 minutes. No raw event stream, full URLs, or direct personal identifiers are retained.

The traffic chart adapts from daily to weekly/monthly bins, explicitly starts its count scale at zero, and provides exact values by hover/focus/tap plus a table. Sessions are deduplicated within each bin (never summed from daily unique counts). Partial intervals are labeled. The audience matrix uses a fixed 0–100% engagement-rate scale with numerator/denominator counts and low-sample labels, avoiding the misleading appearance that larger acquisition sources inherently generate stronger interest. Card CTR includes 95% Wilson intervals on a common 0–100% scale, a low-sample label, and a 20-impression threshold when sorting by CTR. Ranked transitions use a simple origin/destination table rather than a diagram that would obscure exact counts.

The Upstash resource is `personal-website-analytics`, free plan, automatic paid upgrades and eviction disabled. Provider command/bandwidth limits can still stop collection; check the Upstash dashboard and Vercel endpoint errors as traffic grows. Do not enable paid upgrades without approval. Client analytics is inherently forgeable; the collector is not a billing, fraud, or security audit log.

The public `/privacy` page explains collection and offers a browser opt-out; the website footer links to it. Query strings, fragments, outbound URL paths, mail addresses and form values are not collected. Use campaign tags without personal data. DNT and Global Privacy Control suppress collection at both client and server.

## Verification and release

For a reproducible browser/integration fixture, install Redis, run `npm run build`, then `node scripts/analytics-local.mjs --seed` in one terminal and `node test/analytics-integration.mjs` in another. This is loopback-only synthetic data; the local review key is `local-review-key-only`. Stop the fixture with Ctrl-C.

Run `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`. `test/analytics.test.cjs` covers token forgery/expiry/revocation, password and origin checks, input minimization, attribution, cumulative heartbeat aggregation, card denominators, dimensions and journey adjacency.

Before release, exercise the production build with isolated Redis data: signed-out report must return 401; login must set HttpOnly/Secure/SameSite=Strict; authenticated HTML must contain the dashboard, not the login form; logout must remove access; forged cookies and cross-origin requests must fail. Test collection, duplicate retries, malformed/oversized bodies, owner/DNT/GPC suppression, persistent long-term history, compaction and cap warnings. Inspect desktop/mobile and both website color schemes.

Deploy only analytics files. The working tree also contains unrelated content and detail-page edits; do not include those unintentionally. Verify the same authorization and first-party collection behavior on the canonical production domain after deployment. Synthetic local fixtures must never be inserted into production analytics.

## Presentation history and engaged-visit funnel

Schema 2 captures the actual exposed card’s stars, visual position (top-to-bottom, then left-to-right), grid columns/span, rounded rendered dimensions, rounded viewport, initial-viewport placement, and active category route. Immutable snapshots retain the deployment commit, a hash of the Markdown file, and a hash of the selected media references. The latter identifies thumbnail/hero/poster/embed references, not image bytes; continue using new filenames for changed images. Shelf cards fingerprint their hero image. Production deployment commits and repository history allow review of the corresponding content/design. Local builds use a deterministic layout-source hash.

The report’s `presentationFunnel` and dashboard distinguish qualified exposure → attributed card click → confirmed same-tab destination view → destination view with at least 10 active seconds. A short-lived tab-local navigation token joins an exact originating view and click to the intended destination within two minutes. Only the first confirmed arrival per exposure earns credit. Direct visits, unrelated subsequent visits, external links, and new-tab arrivals cannot be inferred as conversions. Destination engagement uses maximum cumulative attention; continuation means a subsequently observed different page in the same session and selected range, not proof of causal influence.

Exposure timestamps determine the selected cohort; clicks, arrivals, and continuation must also fall inside the selected range. Destination attention is cumulative as of the report, including later heartbeats for those views; it is not an end-of-period snapshot. Recent exposures have less opportunity to mature. Source/device/country describe the originating session; category filters select the exposed card’s category while preserving the originating page. Engaged visits per 100 qualified exposures is the primary comparison, with counts, 95% Wilson intervals, and low-sample notices. These are observational rates, not randomized estimates of layout effects.

Old unversioned exposures remain in existing analytics but are excluded from this funnel and explicitly counted as legacy. Nothing is backfilled. Each view stores at most 200 immutable presentations and 100 navigation records; limits produce coverage warnings. Reports expose the top 500 presentation groups with explicit omitted-group/exposure counts; totals cover all eligible groups, while displayed card aggregates cover returned groups only. Browser batches are bounded by both event count and byte size. Sampling runs once per second while visible, with IntersectionObserver invalidating interrupted exposure; it does not add performance telemetry.

Monthly reviews should compare recorded variants within similar source/device/category contexts, distinguish measurement versions, inspect confidence intervals and coverage, and propose a controlled change with a measurable success criterion. Do not infer historical stars or thumbnails from today’s metadata. Small samples warrant a hypothesis and a collection plan rather than a confident recommendation.

## Owner IP exclusion

`ANALYTICS_EXCLUDED_IP_HASHES` is an optional, server-only, comma-separated list of HMAC-SHA256 values generated by `exclusionHash` in `src/lib/analytics/exclusions.ts`, using `ANALYTICS_SESSION_SECRET`. Configure it as sensitive in Vercel Production. Never commit raw owner addresses or hashes. The collector trusts only Vercel's `x-vercel-forwarded-for` platform header, normalizes IPv4/IPv6 (including IPv4-mapped IPv6), and drops matching requests before rate limiting or storage. It does not add any storage lookups to collection. Exclusions apply even when the owner is signed out; other visitors retain normal collection. Non-Vercel runtimes do not trust forwarded IP headers.

Exclusion is exact-address, not a subnet ban. It covers everyone sharing that public IP; a changed network, VPN, ISP address, or IPv6 privacy address may require an updated hash. Keep the browser opt-out or owner sign-in for those cases. Regenerate exclusion hashes whenever the session secret rotates, and redeploy after changing the environment variable. Previous visits cannot be deleted by IP because stored events have no IP-to-view mapping; do not delete guessed sessions or all history.
